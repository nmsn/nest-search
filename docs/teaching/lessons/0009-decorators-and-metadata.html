1. 装饰器是什么(把"魔法"先拆掉)

TypeScript 装饰器,就是函数。没有别的。

看 @Get('/api/users') 这个看起来神秘的写法,展开后是:

// 你写的:
class UserController {
  @Get('/api/users')
  list() { ... }
}

// 编译后实际执行的:
class UserController {
  list() { ... }
}
__decorate([
  Get('/api/users'),  // ← 装饰器工厂返回的函数被调用
  __metadata("design:type", Function),
  __metadata("design:paramtypes", []),
  __metadata("design:returntype", undefined)
], UserController.prototype, 'list', undefined);

看清楚了吗?装饰器就是一个函数,在类定义时被调用,接收被装饰的东西(target / key / descriptor),可以读 / 写 metadata,可以替换函数实现。

4 种装饰器签名(必须背下来)

// 1. Class 装饰器 — 装饰整个类
function MyDecorator(constructor: Function) {
  // 可以修改类、追加属性、注册到全局表
}

// 2. Method 装饰器 — 装饰方法
function MyDecorator(
  target: any,           // 类原型
  propertyKey: string,   // 方法名
  descriptor: PropertyDescriptor,  // 方法的描述符
) {}

// 3. Property 装饰器 — 装饰属性
function MyDecorator(
  target: any,
  propertyKey: string,
) {}

// 4. Parameter 装饰器 — 装饰方法参数(很少单独用,NestJS 用它)
function MyDecorator(
  target: any,           // 类原型
  propertyKey: string,   // 方法名
  parameterIndex: number,// 第几个参数
) {}

四种装饰器参数不一样,这是后面写自定义装饰器时要背的"契约"。

2. reflect-metadata 协议 — 装饰器怎么"互相通信"

现在有个问题:NestJS 怎么知道 @Injectable() 修饰的类构造函数需要哪些参数?

逻辑上,装饰器之间不通信:@Injectable() 不知道类构造函数签名,@Inject('SOME_TOKEN') 不知道类在哪里。NestJS 是在运行时用 reflect-metadata API 读取的。

基本 API

import 'reflect-metadata';

// 写
Reflect.defineMetadata('key', 'value', target);

// 读
const v = Reflect.getMetadata('key', target);

// 类型化(看 key 上的 generic 知道是什么类型)
Reflect.defineMetadata<string>('path', '/api/users', UserController.prototype.list);

NestJS 用了哪些"标准 key"

你不需要记,但要知道存在:

  • design:paramtypes — 构造函数参数类型列表(NestJS 拿这个做自动 DI)
  • design:type — 属性 / 方法的类型
  • design:returntype — 方法返回类型
  • path — 路由路径(@Get('/api/users') 写的)
  • method — HTTP 方法

这些都是 NestJS 自定义的 metadata key,不是标准 — 是社区/框架约定的。

为什么需要 "emitDecoratorMetadata": true

这是 tsconfig.json 里的开关。它让 TypeScript 编译器在编译期自动 emit Reflect.defineMetadata('design:paramtypes', [...], class) 这种调用,把构造函数签名"写进"编译产物。否则运行时读不到类型,自动 DI 失效。

这是 NestJS 项目的必备开关(项目已经开了)。

3. NestJS 装饰器内幕 — 看 5 行源码

装饰器不魔法,魔法在"运行时 + reflect-metadata + 工厂函数"。看 NestJS 几个核心装饰器的简化实现:

@Get(路由路径)

// 简化版(从 @nestjs/common 抽出来的本质)
export function Get(path: string = ''): MethodDecorator {
  return (target, key, descriptor) => {
    Reflect.defineMetadata('path', path, descriptor.value);   // 存 path
    Reflect.defineMetadata('method', 'GET', descriptor.value); // 存 method
  };
}

就这两步 — "贴 metadata"。NestJS 启动时扫所有 method,根据 path + method 挂到 Express 上。

@Injectable()(自动 DI 的核心)

export function Injectable(): ClassDecorator {
  return (target) => {
    // 不需要存任何东西!关键在 tsconfig 开了 emitDecoratorMetadata
    // 编译时自动加:
    //   Reflect.defineMetadata('design:paramtypes', [LoggerService, ConfigService], target);
    // 所以 NestJS 运行时能读到"这个类构造函数需要 LoggerService 和 ConfigService"
  };
}

这是 NestJS 自动 DI 的核心 — 装饰器本身不做任何事,关键是 tsc 自动 emit 的元数据。

@Inject(TOKEN)

export function Inject(token: string): ParameterDecorator {
  return (target, key, parameterIndex) => {
    Reflect.defineMetadata('self:paramtypes', ..., ...);  // 标记"这个参数用 token 取"
    // NestJS 看到这个 metadata 就去容器里找 token 对应的 instance
  };
}

4. 动手 · 30 行代码还原 NestJS

新建 apps/gateway/src/decorators-demo/index.ts,一个文件做完 4 个装饰器 + 迷你 IoC 容器 + 一个 demo:

4.1 · 单文件 demo:30 行还原 NestJS 路由 + DI

新建文件 apps/gateway/src/decorators-demo/index.ts:

import 'reflect-metadata';

// ========== 1. 4 个装饰器(简化版 NestJS 实现) ==========

function Controller(prefix: string = ''): ClassDecorator {
  return (target) => {
    Reflect.defineMetadata('prefix', prefix, target);
  };
}

function Get(path: string = ''): MethodDecorator {
  return (target, key, descriptor) => {
    Reflect.defineMetadata('path', path, descriptor.value);
    Reflect.defineMetadata('method', 'GET', descriptor.value);
  };
}

function Injectable(): ClassDecorator {
  return (target) => {
    // 关键:不做事。依赖 tsc 的 emitDecoratorMetadata 自动写 design:paramtypes
  };
}

function Inject(token: string): ParameterDecorator {
  return (target, key, parameterIndex) => {
    const existing = Reflect.getMetadata('custom:paramtypes', target, key) || [];
    existing[parameterIndex] = token;
    Reflect.defineMetadata('custom:paramtypes', existing, target, key);
  };
}

// ========== 2. 迷你 IoC 容器 ==========

const container = new Map<any, any>();

function resolveDependencies(target: any): any[] {
  // 读 tsc 自动 emit 的 design:paramtypes(构造函数参数类型列表)
  const paramTypes: any[] = Reflect.getMetadata('design:paramtypes', target) || [];
  // 也读自定义的 @Inject 标记
  const customTypes: any[] = Reflect.getMetadata('custom:paramtypes', target.prototype, undefined) || [];
  return paramTypes.map((type, i) => {
    if (customTypes[i]) {
      // @Inject(TOKEN) 优先
      return container.get(customTypes[i]) ?? createInstance(type);
    }
    return createInstance(type);
  });
}

function createInstance(target: any): any {
  if (container.has(target)) return container.get(target);
  const deps = resolveDependencies(target);
  const instance = new target(...deps);
  container.set(target, instance);
  return instance;
}

function bootstrap(controllerClass: any) {
  const prefix = Reflect.getMetadata('prefix', controllerClass) || '';
  // 扫所有 method,挂到 fake router
  const proto = controllerClass.prototype;
  Object.getOwnPropertyNames(proto).forEach((methodName) => {
    const method = proto[methodName];
    const path = Reflect.getMetadata('path', method);
    const method_ = Reflect.getMetadata('method', method);
    if (path && method_) {
      console.log(`[路由注册] ${method_} ${prefix}${path}  →  ${controllerClass.name}.${methodName}`);
    }
  });

  // 实例化 controller(顺便验证 DI)
  const instance = createInstance(controllerClass);
  console.log(`[controller 实例化] ${controllerClass.name} 的依赖:`,
    resolveDependencies(controllerClass).map((d) => d.constructor.name));
  return instance;
}

// ========== 3. demo ==========

@Injectable()
class UserService {
  getAll() { return ['alice', 'bob']; }
}

@Injectable()
class LoggerService {
  log(msg: string) { console.log(`[log] ${msg}`); }
}

@Controller('/api/users')
class UserController {
  constructor(
    private userService: UserService,
    private logger: LoggerService,
  ) {}

  @Get('/list')
  list() {
    this.logger.log('list called');
    return this.userService.getAll();
  }
}

bootstrap(UserController);

4.2 · 跑 demo

用项目已有的 ts-node(已在 devDependencies)跑:

npx ts-node apps/gateway/src/decorators-demo/index.ts

期望输出:

[路由注册] GET /api/users/list  →  UserController.list
[controller 实例化] UserController 的依赖: [ UserService, LoggerService ]

两个值表示:

  • 扫描类方法,读出 path + method metadata → 自动注册路由
  • 实例化时读 design:paramtypes → 自动注入 UserService + LoggerService

这就是 NestJS 路由 + DI 的本质。NestJS 实际代码更长(带模块系统、scope 控制、循环依赖检测…),但核心机制就是你看到的 30 行。

4.3 · 试错:把 emitDecoratorMetadata 关闭看效果

为了看 emitDecoratorMetadata 的关键作用,我们做对比实验:

  1. 打开 tsconfig.json,把 emitDecoratorMetadata 暂时改成 false
  2. 重新跑 npx ts-node apps/gateway/src/decorators-demo/index.ts
  3. 期望: UserController 的依赖 那一行打印 [] — 因为编译时没写 design:paramtypes,运行时读不到参数类型
  4. 改回 true,重启 → 正常

这是为什么"没开 emitDecoratorMetadata 时 NestJS 自动 DI 失效"的根源。

4.5 · 实战:给 nest-search 写 @Roles() 装饰器

理论是抽象的,实践才出真知。把 0004 那个 @Public() 装饰器从"0 业务逻辑"升级为"携带参数" — 写一个真正能用的 @Roles(...) 装饰器。

5.1 · 新建 roles.decorator.ts

新建 apps/gateway/src/common/decorators/roles.decorator.ts:

import { SetMetadata } from '@nestjs/common';

export const ROLES_KEY = 'roles';

/**
 * 给 handler 标记"需要哪些角色才能访问"
 * 用法: @Roles('admin', 'editor')
 */
export const Roles = (...roles: string[]) => SetMetadata(ROLES_KEY, roles);

对比 0004 的 @Public():唯一区别是工厂函数接 rest 参数 ...roles。就这么简单 — SetMetadata 把 roles 数组写到 metadata,谁读是读的人的事。

5.2 · 改 app.controller.ts,挂到 syncFull

打开 apps/gateway/src/app.controller.ts:

  1. 顶部加 import:
    import { Roles } from './common/decorators/roles.decorator';
  2. 在 syncFull 上加 @Roles('admin', 'editor'):
    @ApiOperation({ summary: "触发全量同步(管理员)" })
@ApiParam({ name: "businessLine", example: "ds" })
@ApiResponse({ status: 200, description: "同步任务已启动" })
@ApiResponse({ status: 403, description: "非管理员" })
@Roles('admin', 'editor')     // ← 新加
@UseGuards(AdminGuard)
@Post("api/sync/full/:businessLine")
async syncFull(@Param("businessLine") bl: string) {
  return this.proxyService.forward("sync", "POST", `/api/sync/full/${bl}`);
}

现在 syncFull 的 metadata 里有:
'roles' = ['admin', 'editor']
'path' = '/api/sync/full/:businessLine'(0004 装的)
'method' = 'POST'(0004 装的)

5.3 · 验证 metadata 真的写上了(用 script,不走 HTTP)

写一个一次性 script,直接读 metadata — 不走 HTTP、不走 guard、最干净。

新建 apps/gateway/src/decorators-demo/check-roles.ts:

import 'reflect-metadata';
import { AppController } from '../app.controller';

console.log('=== 验证 @Roles metadata 是否真的写到 method 上 ===\n');

const syncFullRoles = Reflect.getMetadata('roles', AppController.prototype.syncFull);
console.log('syncFull roles:', syncFullRoles);

const syncFullPath = Reflect.getMetadata('path', AppController.prototype.syncFull);
console.log('syncFull path:', syncFullPath);

const syncFullMethod = Reflect.getMetadata('method', AppController.prototype.syncFull);
console.log('syncFull method:', syncFullMethod);

const listFormsRoles = Reflect.getMetadata('roles', AppController.prototype.listForms);
console.log('\nlistForms roles (期望 undefined):', listFormsRoles);

跑:

npx ts-node apps/gateway/src/decorators-demo/check-roles.ts

期望输出:

syncFull roles: [ 'admin', 'editor' ]
syncFull path: api/sync/full/:businessLine
syncFull method: 1
listForms roles (期望 undefined): undefined

解读:

  • roles: [ 'admin', 'editor' ] ✅ @Roles 写上了
  • method: 1 是 NestJS RequestMethod.POST 的 enum 值(不是字符串 "POST")
  • path 不带前导 / 是 NestJS 设计(启动时拼上)
  • listForms roles: undefined ✅ @Get 没有 @Roles,符合预期

之前版本的 5.3 写的是"用 console.error + curl",但 @UseGuards(AdminGuard) 会在 handler 之前拒绝请求,console.error 永远跑不到。这个 script 方案不走 HTTP 不走 guard,直接读 metadata,稳。
