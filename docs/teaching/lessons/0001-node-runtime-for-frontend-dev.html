你是一个 8 年的前端工程师。你熟悉 Chrome 的 V8、熟悉 fetch、熟悉 React 的渲染模型。下面这张表是 Node 和浏览器在底层能力上的几个关键差异 — 知道这些,你后面看到 NestJS 任意一段代码都不会慌。

1. 事件循环:30 秒版本

Node 是单线程(只有一个主线程执行 JS),但它是非阻塞的。这个"非阻塞"靠的是 libuv(底层 C 库)+ 一个循环,叫事件循环(event loop)。

你跑 node main.js 时,NestJS 的 bootstrap() 会被调用一次,然后 Node 进入事件循环 — 等任务、取任务、执行任务、回到"等"。每次循环叫一个 tick。

   ┌───────────────────────────┐
┌─▶│        timers             │ ← setTimeout / setInterval 回调
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
│  │     pending callbacks     │ ← I/O 回调(上一轮延后的)
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
│  │       idle, prepare       │ ← 内部用,通常忽略
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
│  │          poll             │ ← 取出新 I/O 事件,执行回调
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
│  │          check            │ ← setImmediate 回调
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
│  │  close callbacks          │ ← socket.on('close')
│  └─────────────┬─────────────┘
└──┘                              一个 tick 完成,回到 timers

三条需要记住的铁律:

  1. 每个 phase 都有自己的 FIFO 队列,phase 跑完才进下一个 phase
  2. process.nextTick 和 Promise.then 是微任务,在每个 phase 切换之间清空 — 永远比 timers 跑得早
  3. I/O 是异步的:你调用 fs.readFile,Node 不会卡住主线程;它把活交给 libuv 的线程池,完成后把回调塞进 pending callbacks

权威来源:[Node.js Docs — The Node.js Event Loop](https://nodejs.org/en/docs/guides/event-loop-timers-and-nexttick)。第一次看可能糊,正常,后面每节课都会回来引用它。

2. 这个项目里的 module / require / process

打开 package.json 找 "type": "commonjs" — 这意味着这个项目用的是 CommonJS 模块系统(不是 ESM)。所以:

  • 你看到的 require('express') 不是 ES Module 的 import,是 CJS 的同步加载
  • module.exports = ... 不是 export default ...
  • 每个 .ts 文件被 tsc 编译后,顶部会多出一段 __decorate / __metadata — 那是装饰器(后面课讲)

现在看 apps/gateway/src/main.ts 这段:

const port = process.env.GATEWAY_PORT || 3000;
await app.listen(port);
console.log(`Gateway running on port ${port}`);

三个"在浏览器里没有"的东西出现了:

  • process.env.GATEWAY_PORT — 从环境变量读配置,12-factor app 的核心约定。生产环境里这个值是 K8s/Docker 注入的,本地开发它就是 undefined,所以 || 3000 兜底
  • __dirname(没出现但马上会用)— 当前文件所在的绝对目录,常用于读同目录的配置文件
  • process.cwd() — Node 进程启动时所在的工作目录,通常就是 pnpm start:gateway 执行的位置

权威来源:[Node.js Docs — Process](https://nodejs.org/api/process.html) 和 [Node.js Docs — CommonJS modules](https://nodejs.org/api/modules.html)。

4. 你今天该交的一行代码

Commit · 5 分钟

在 apps/gateway/src/main.ts 里,在 await app.listen(port) 之前加一行:

console.log('cwd:', process.cwd(), 'env.PORT:', process.env.PORT);

重启 pnpm start:gateway,观察控制台 — 你会看到 Node 进程的工作目录和当前环境里所有跟 PORT 相关的变量(包括 PATH、SHELL 这种无关的)。

你在验证什么: process.cwd() 跟你 pwd 命令输出一致,说明 Node 不是"在 gateway 目录里"运行,而是"在 pnpm start:gateway 触发的 cwd 里"运行 — 这是后面所有"读配置 / 读证书 / 写日志"路径问题的根。

下一节预告

你刚刚把 Node 跑起来了,但还没碰异步错误。一个 Node 进程如果 throw 了一个 unhandled rejection,默认行为是让进程退出 — 这就是为啥我们经常看到生产上 Node 服务"莫名其妙挂了"。Lesson 0002 我们会在 gateway 里故意 throw 一个 promise rejection,然后用 unhandledRejection 钩子接住它,顺便把"为什么 NestJS 要把 enableShutdownHooks() 打开"讲清楚。
