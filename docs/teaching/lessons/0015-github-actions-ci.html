1. 什么是 CI — "自动化测试闸口"

你 0013 + 0014 已经写了 18 个测试,本地 pnpm test 全绿。但这不够。

现实场景:

  • 同事提了 PR,你 review 通过 → merge → master 跑挂了(他本地没跑测试)
  • 你 push 一个改动,本地测试通过 → CI 跑挂(本地 Node 版本 / 缓存状态不一样)
  • 你 push 一个改动,本地测试通过 → CI 跑挂(本地有 docker MySQL,CI 没有)

CI = 每次 push / PR 都自动跑一次测试,跑不过就 merge 阻塞。这才是"代码永远绿"的真闸口。

2. GitHub Actions 基础 — workflow / job / step / service

GitHub Actions 是 GitHub 内置的 CI。每个 workflow 是一个 YAML 文件,放在 .github/workflows/ 下。

2.1 4 个核心概念

workflow    ← 一个 YAML 文件(我们写 test.yml)
  └─ job    ← 一个 runner 上跑的工作单元(ubuntu / windows / macOS)
       └─ step   ← 一个具体动作(checkout / setup / run script)
       └─ service ← 跟 job 一起启动的容器(MySQL / Redis)

2.2 Service container 是什么

关键能力:在 CI 里跑真 MySQL / Redis,不用装在 runner 上。GitHub Actions 用 Docker 起服务容器,端口映射到 localhost — 跟本地 docker-compose up 完全一致。

这意味着:你 nest-search 的 DATABASE_URL=mysql://root:root123@localhost:3306/nest_search,本地能跑,CI 也能跑。零代码改动。

3. 写 workflow — service container 是核心

3.1 · 新建 .github/workflows/test.yml

name: test

# 触发时机:push 到 main + 所有 PR
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

# 取消同分支上一次 in-progress run(避免重复排队)
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    name: unit + e2e tests
    runs-on: ubuntu-latest

    # ← 核心:service containers 提供真 MySQL + Redis
    # GitHub Actions 把容器端口映射到 localhost,跟本地 docker-compose 一致
    services:
      mysql:
        image: mysql:8.0
        env:
          MYSQL_ROOT_PASSWORD: root123       # 跟 apps/auth-service 默认 DATABASE_URL 匹配
          MYSQL_DATABASE: nest_search       # 同上,自动建库
        ports:
          - 3306:3306
        # 健康检查 — GitHub Actions 等健康才让下一步跑
        options: >-
          --health-cmd="mysqladmin ping -h localhost -uroot -proot123"
          --health-interval=10s
          --health-timeout=5s
          --health-retries=5

      redis:
        image: redis:7-alpine
        ports:
          - 6379:6379
        options: >-
          --health-cmd="redis-cli ping"
          --health-interval=10s
          --health-timeout=5s
          --health-retries=5

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup pnpm
        uses: pnpm/action-setup@v4
        with:
          version: 9.15.0   # 跟 package.json packageManager 一致

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'pnpm'    # 自动 cache pnpm store,跑得快 50%

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      # 双保险:service container 的 healthcheck 跟 Drizzle 连接之间可能还有缝隙
      # 等最多 30 秒确保 MySQL 完全 ready
      - name: Wait for MySQL
        run: |
          echo "Waiting for MySQL to be ready..."
          for i in {1..30}; do
            if mysqladmin ping -h 127.0.0.1 -uroot -proot123 --silent 2>/dev/null; then
              echo "MySQL is ready"
              break
            fi
            sleep 1
          done

      - name: Run tests + coverage
        run: pnpm test:cov

      - name: Upload coverage report
        if: always()    # 即使测试失败也上传,方便排查
        uses: actions/upload-artifact@v4
        with:
          name: coverage-report
          path: coverage/
          retention-days: 7

3.2 · 5 个值得讲的设计选择

选择为什么
mysql:8.0 不是 latestlatest 标签会变;锁版本,CI 才稳定
MYSQL_ROOT_PASSWORD=root123跟 nest-search auth-service 默认 DATABASE_URL 一致;零代码改动
concurrency.cancel-in-progress: true同分支 push 第二次取消第一次,省 CI 分钟
pnpm/action-setup@v4 version: 9.15.0跟 package.json#packageManager 一致
if: always() + upload-artifact失败也上传 coverage,方便排查覆盖率

3.3 · 本地验证 workflow(用 act)

不 push 也能跑 CI:nektos/act 在本地用 Docker 模拟 GitHub Actions runner。

brew install act
act -j test           # 跑 test job
act -j test --dryrun  # 只看 workflow,不真跑(调试用)

但 act 跑 service containers 有局限(Mac 上 Docker 跟 Linux runner 行为不完全一致),最权威验证还是 push 到远端。
