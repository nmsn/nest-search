1. 错误的三种"出口"

Node 把错误分成三个互不重叠的家族。混淆它们是 backend 新手最常见的"为什么我的错误没被处理"的根因。

家族 A:同步 throw
在调用栈上被 try/catch 接住,或者冒泡到事件循环外变成 uncaughtException。
作用域: 当前调用栈。
家族 B:错误优先回调(error-first callback)
Node 老 API 风格 fs.readFile(path, (err, data) => ...),错误是参数,不是 throw。
作用域: 调用者注册的回调。NestJS 几乎不直接用,但内部库会用(比如 ioredis 早期版本)。
家族 C:Promise rejection
Promise 被 reject 但没人在 .then(onFulfilled, onRejected) / .catch() / await 里接住时,会变成 unhandledRejection。
作用域: 进程级事件,不在任何请求的处理链上。

关键点: A 走调用栈,C 走事件队列。它们的"漏出去"的兜底机制完全不同 — 这就是为什么我们要把 process.on('unhandledRejection') 单独提出来讲。

2. NestJS 异常流的 5 层

当一个 HTTP 请求进入 NestJS,错误可能在这 5 层中的某一层被处理(也可能漏出去):

请求进 ─▶ Guard ─▶ Interceptor ─▶ Pipe ─▶ Controller.handler ─▶ Service
                                          │
                                          │ throw new HttpException(...)
                                          ▼
                                NestJS 内置 Catch ─▶ ExceptionFilter
                                          │              ▲
                                          │              │ 我们写的 AllExceptionsFilter
                                          ▼              │
                                      HTTP Response (JSON) ─▶ 客户端

只有当 throw 发生在请求上下文内(Guard / Pipe / Controller / Service 调用链),NestJS 才会把它路由到 AllExceptionsFilter.catch()。其它地方 — 比如 setTimeout 回调、EventEmitter 监听器、第三方库内部的 Promise — NestJS 看不见。

打开现在项目的 apps/gateway/src/filters/all-exceptions.filter.ts:

export class AllExceptionsFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    // ... 把 exception 翻译成 HTTP 响应
  }
}

它确实写得不错 — 区分 HttpException(可控)和其他(不可控),返回统一格式。但它没打日志。意思是:每次出 500,你的控制台是干净的,你只能靠事后看 access log 反推,没有 stack、没有发生时间、没有上下文。

3. NestJS 看不到的世界

考虑下面这段伪代码(在 controller 外面执行):

// 启动时排个延时任务
setTimeout(() => {
  fetch('http://downstream-service/some-api')   // 假设这是个会 reject 的 promise
    .catch(err => logger.error(err));            // 我们写了 catch
}, 5000);

// 几个月后,有人重构时把 .catch 删了
setTimeout(() => {
  fetch('http://downstream-service/some-api')   // ← 没 catch
}, 5000);

这个 fetch reject 时,Node 会发出 'unhandledRejection' 事件。NestJS 完全不知道这件事发生过。默认行为(在 Node 15+):打印到 stderr,下一次事件循环时让进程退出(退出码 1)。

权威来源: [Node.js Docs — process: 'unhandledRejection' event](https://nodejs.org/api/process.html#warning-using-uncaughtexception-correctly)。Node 15+ 默认 --unhandled-rejections=throw。

"让进程退出"听起来激进,但实际上**这是你想要的行为**。理由:你的服务已经进入了"不知道自己不知道"的状态 — 不知道哪个请求没被处理、不知道状态是否一致、不知道连接池是否泄漏。让进程死掉、让 K8s 重启、让健康检查拉黑、让告警响起,比"带着内存泄漏和连接泄漏继续服务下一个请求"安全得多。

4. 进程级钩子

Node 给你两个钩子去拦截这类灾难:

process.on('unhandledRejection', (reason, promise) => {
  console.error('[unhandledRejection]', reason);
  // 强烈建议:这里不要尝试恢复。记日志,然后让进程退出。
  process.exit(1);
});

process.on('uncaughtException', (err) => {
  console.error('[uncaughtException]', err);
  process.exit(1);
});

几个生产级约定:

  1. 永远 log 完整 stack(上面的 console.error(err) 会自动展开 stack)
  2. 永远在钩子里调 process.exit(默认行为虽然会退出,但显式退出可以让你控制退出码和清理顺序)
  3. 不要在这里面 throw — 会触发另一个 uncaughtException,雪崩
  4. NestJS 11 的 app.enableShutdownHooks() 会拦截 SIGTERM / SIGINT,这跟我们今天的钩子互补但不冲突(下节课讲)

5. 动手 · 30 分钟

这是本节课的实质部分 — 三个改动,每个都在 1-3 行内。完成后跑起来验证,然后我们 0002 末尾的 commit 命令一次性收口。

5.1 · 在 main.ts 加进程级钩子

打开 apps/gateway/src/main.ts,在 bootstrap() 之前(文件顶部,import 之后)加两段:

process.on('unhandledRejection', (reason) => {
  console.error('[unhandledRejection]', reason);
});
process.on('uncaughtException', (err) => {
  console.error('[uncaughtException]', err);
});

注意: 这里我们不调 process.exit。gateway 是生产服务的入口,本课目的是"让异常显形 + 不让进程爆炸" — 是否退出留给 NestJS 的 enableShutdownHooks(下节课)来管。

5.2 · 在 AllExceptionsFilter 加一行日志

打开 apps/gateway/src/filters/all-exceptions.filter.ts,在 catch() 方法最前面加一行:

catch(exception: unknown, host: ArgumentsHost) {
  console.error('[AllExceptions]', exception);
  // ... 原有逻辑
}

注意我们 log 的是 exception 对象,不是 exception.message — 因为 console.error 会展开 stack 和类型,后者只给字符串。

5.3 · 验证三个路径

  1. 重启 pnpm start:gateway
  2. 路径 1(同步 throw,应该被 filter 接住):
    临时改 app.controller.ts 的 health():
    @Get('health')
health() {
  throw new Error('boom-sync');
}
    curl -i http://localhost:3000/health — 期望:500 + body 含 "boom-sync",控制台看到 [AllExceptions] 日志
  3. 路径 2(Promise reject,应该被 process.on 接住):
    还原 health(),改成:
    @Get('health')
async health() {
  Promise.reject(new Error('boom-async-no-catch'));
  return { status: 'ok' };
}
    curl -i http://localhost:3000/health — 期望:200(因为 handler 本身没 throw),但控制台立刻看到 [unhandledRejection] Error: boom-async-no-catch
  4. 路径 3(完全对照):
    还原成原版 return { status: 'ok', ... },再 curl 一次,确认控制台是干净的

三个路径都验证到了,你就有了一张完整的"错误家族"图:

  同步 throw ───────▶ [AllExceptions] 日志  ──▶ HTTP 500 响应
                       ▲
                       │ NestJS 异常管道
                       │
  Promise reject  ────▶ process.on('unhandledRejection')  ──▶ 仅日志
  (无 catch)            ▲
                       │ 进程级事件
                       │
  throw 在 setTimeout  ──▶ 同上

下一节预告

你刚刚让"漏出去的异常"显形了,但还缺一块 — 进程在收到 SIGTERM(K8s 滚动升级)时,会怎么死?默认是"硬死":所有进行中的连接断掉,RabbitMQ consumer 不发 ack,Redis 连接不释放,新的请求进来发现 socket 没了。Lesson 0003 · Node 进程生命周期: 加 app.enableShutdownHooks()、看 NestJS 怎么协调 SIGTERM、对比"硬死 vs 软死"的时间线。
