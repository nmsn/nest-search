```
  ✅ "剩余 error budget 80%, 这个 bug 不紧急"
```

## §2. SLI / SLO / SLA 区别

### 2.1 SLI（Service Level Indicator）= 指标

```
SLI = 服务的"测量指标"
比如:
  - 响应时间 P95
  - 错误率
  - 吞吐量
  - 可用性
```

### 2.2 SLO（Service Level Objective）= 目标

```
SLO = 对 SLI 的"目标值"
比如:
  - P95 响应 < 500ms （SLI 是 P95 响应, SLO 是 < 500ms）
  - 错误率 < 0.1%
  - 可用性 99.9%
```

### 2.3 SLA（Service Level Agreement）= 协议

```
SLA = 对客户的"承诺 + 赔偿条款"
比如:
  - 99.9% 可用（合同）
  - 达不到赔钱
  - 99.99% 通常 SLA 比 SLO 更严
```

### 2.4 三者关系

```
SLA (合同承诺) ≥ SLO (内部目标) > SLI (实际测量)

例:
  SLA: 99.9%（合同承诺,达不到赔钱）
  SLO: 99.95%（内部目标, 比 SLA 高一点留 buffer）
  SLI: 当前 99.97%（实际测量）

  99.97% > 99.95% > 99.9% ✅
```

## §3. 常用 SLO 指标

### 3.1 可用性（Availability）

```
公式: (总时间 - 不可用时间) / 总时间

99.9% (3 个 9) → 每月不可用 ≤ 43.83 分钟
99.99% (4 个 9) → 每月不可用 ≤ 4.38 分钟
99.999% (5 个 9) → 每月不可用 ≤ 26 秒

记忆: 每多一个 9, 不可用时间除以 10
```

### 3.2 延迟（Latency）

```
SLO: P95 / P99 响应时间

为什么用 P95 / P99 不用平均:
  - 平均会被极端值拉高
  - P95 = 95% 用户在 X ms 内得到响应
  - 用户视角的真实体验

常见值:
  - 实时搜索: P99 < 200ms
  - 普通 API: P95 < 500ms
  - 后台任务: P50 < 5s
```

### 3.3 错误率（Error Rate）

```
SLO: 错误请求 / 总请求 < X%

注意:
  - 5xx 算错误
  - 4xx 通常不算（客户端问题）
  - 但 401/403 业务定义可调
```

### 3.4 吞吐量（Throughput）

```
SLO: 每秒能处理多少请求（RPS/QPS）

注意:
  - 峰值 vs 平均
  - 业务目标: 1000 RPS? 10000 RPS?
  - 超过 SLO = 排队 / 失败
```

## §4. Error Budget（错误预算）

### 4.1 是什么？

```
Error Budget = 允许的"失败额度"
SLO 99.9% → 0.1% 时间可以挂（每月 43.83 分钟）

含义:
  - 服务可以在 Error Budget 内失败
  - 用完了就要"停止新功能, 专注稳定性"
  - 防止无止境追求 100% 稳定（成本太高）
```

### 4.2 怎么用？

```
场景: Error Budget 30 天内剩余 80%

  → 还可以失败 8.77 分钟
  → 这次挂了 5 分钟 → 还有 3.77 分钟
  → 这周发布新功能 5 次, 每次导致 1 分钟故障
  → 还能继续

场景: Error Budget 30 天内剩余 10%

  → 只剩 4.38 分钟
  → 冻结发布新功能
  → 团队 focus 稳定性
```

### 4.3 Google 内部实践

```
- 100% 不可达（成本 10x）
- 99.9% 可达（合理成本）
- 用 Error Budget 平衡发布和稳定
- SRE 团队和开发团队共用 budget
```

## §5. nest-search SLO 文档

### 5.1 search-service

| 指标 | SLI | SLO | 测量方法 |
|------|-----|-----|----------|
| 可用性 | 1 - 错误率 | 99.5% | uptime / 30d |
| 搜索响应 | P95 响应时间 | < 500ms | k6 / Prometheus |
| 搜索错误率 | 5xx / 总数 | < 1% | 日志统计 |
| 搜索吞吐 | RPS | > 100 RPS | k6 压测 |

**为什么是 99.5% 而不是 99.9%？**
- 内部系统不是钱相关（不像支付）
- 数据可重建（sync-service 可重跑）
- 99.5% 月不可用 ≤ 3.65 小时
- 留出 buffer 应对真实故障

### 5.2 sync-service

| 指标 | SLI | SLO | 测量方法 |
|------|-----|-----|----------|
| 同步成功率 | 成功 / 总数 | > 99% | sync-records 表 |
| 同步延迟 | 入队 → 完成的 P95 | < 60s | 日志 + ts |
| 队列堆积 | waiting 任务数 | < 100 | BullMQ stats |

### 5.3 auth-service

| 指标 | SLI | SLO | 测量方法 |
|------|-----|-----|----------|
| 登录响应 | P95 响应时间 | < 300ms | k6 |
| 登录错误率 | 5xx / 总数 | < 0.5% | 日志 |
| JWT 验证错误率 | 401 / 总数 | < 5% | 日志（5% 算正常,客户端 token 过期）|

### 5.4 gateway

| 指标 | SLI | SLO | 测量方法 |
|------|-----|-----|----------|
| 路由响应 | P95 | < 100ms | 简单转发,低延迟 |
| 路由可用性 | 1 - 错误率 | 99.9% | 上游错误不算 |

### 5.5 form-service

| 指标 | SLI | SLO | 测量方法 |
|------|-----|-----|----------|
| 表单提交响应 | P95 | < 500ms | 日志 |
| 表单提交错误率 | 5xx / 总数 | < 1% | 日志 |

## §6. Error Budget 实践

### 6.1 30 天 error budget 计算

```
search-service SLO 99.5%:

30 天 = 30 × 24 × 60 = 43200 分钟
Error budget = 43200 × 0.5% = 216 分钟 = 3.6 小时

含义:
  1 个月内可以挂 3.6 小时
  超过 = 违反 SLO
```

### 6.2 当 budget 耗尽

```
1. 冻结新功能发布
2. 团队 focus 稳定性
3. 修复历史故障
4. 重新规划 SLO（可能定太低）
```

## §7. 如何测量 SLO

### 7.1 数据源

| 工具 | 作用 |
|------|------|
| Prometheus | 拉指标, 计算 SLI |
| 日志系统 (Pino + ELK) | 错误率统计 |
| uptime 监控 | 可用性计算 |
| k6 / 压测 | 延迟 / 吞吐基线 |

### 7.2 工具链

```
Prometheus 拉 SLI 指标
  ↓
Grafana 画 SLO dashboard
  ↓
Alertmanager 报警（违反 SLO 时）
  ↓
PagerDuty / Slack 通知
```

## §8. 设计决策

### 决策 1 · SLO 应该多严？

```
参考 Google 实践:
  - 99% (2 个 9) → 太松, 不算 SLO
  - 99.9% (3 个 9) → 通用 web
  - 99.99% (4 个 9) → 关键业务
  - 99.999% (5 个 9) → 钱/医疗

nest-search:
  - 内部系统, 不是钱相关
  - 99.5% - 99.9% 足够
  - 太严会花大量成本
```

### 决策 2 · 选哪个 SLI？

```
前端最关心: 响应时间 (P95)
运维最关心: 可用性 (uptime)
业务最关心: 错误率
团队最关心: 错误预算 (error budget)

→ 至少 3 个核心 SLI: 响应 + 可用 + 错误
```

### 决策 3 · 如何在团队推广 SLO？

```
1. 找 1-2 个核心服务先定义
2. 跟产品/老板对齐"稳定性的价值"
3. 用 Error Budget 平衡发布
4. 季度回顾 SLO 合理性
```
