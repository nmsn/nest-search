1. process 对象 — 你的进程自画像

Node 进程里的全局 process 对象是这个进程唯一的自我认知通道。0001 我们摸过 process.cwd() / process.env,这节课把其它常用的一并看:

属性 / 方法类型含义
process.pidnumber当前进程 ID(给 kill 命令用)
process.ppidnumber父进程 ID(在 K8s 里通常是 container runtime)
process.uptime()number进程跑了多少秒
process.argvstring[]命令行参数,argv[0] 是 node 二进制路径,argv[1] 是入口文件
process.envobject环境变量(0001 讲过)
process.cwd()() => string当前工作目录(0001 讲过)
process.memoryUsage()() => objectRSS / heapTotal / heapUsed / external 四个数值,看内存
process.exit(code)(number) => never立即退出,code 是退出码(0 = 正常,1+ = 异常)
process.on(signal, fn)订阅信号§2 讲

记不住没关系 — 留个查表心锚: "我现在的进程怎么了" — 看 uptime / memoryUsage; "我要死了" — 看 §2-§4。

2. 信号家族 — 跟 OS 说话的 5 个词

Unix 信号是进程间最古老的"轻量通知": 内核给进程发一个整数,进程可以忽略、用默认动作处理(通常是退出),或者用代码拦截自己处理。Node 把这些信号映射成 process.on('SIGXXX', handler) 事件。

信号编号触发场景能拦?默认行为
SIGTERM15K8s / systemd / kill <pid> 默认✅退出
SIGINT2Ctrl+C✅退出
SIGHUP1历史: 终端挂断;现代: 重载配置(nodemon 监听这个)✅退出
SIGKILL9kill -9 / K8s 超时兜底❌立即死,内核强制
SIGUSR212用户自定义(NestJS enableShutdownHooks 也监听这个)✅退出

关键事实:SIGKILL 内核级强制,任何代码拦不住。这意味着"用 SIGKILL 关服务 = 没有任何 cleanup 的机会" — 所有 in-flight 请求会收到 502,所有未 ack 的消息会丢,所有未刷盘的日志会没。所以生产环境里"我先 SIGKILL 它"是最后手段,不是常规操作。

权威来源: [Node.js Docs — Process signals](https://nodejs.org/api/process.html#signal-events) 和 [Linux man 7 signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)。

3. K8s 滚动升级的 8 步时间线

你写的这个 gateway 部署到 K8s 之后,运维做一次滚动升级,你这个进程在 8 步内会经历:

第 1 步: kubectl apply / 镜像更新

Deployment spec 更新 ─▶ ReplicaSet 创建新 Pod

第 2 步: 新 Pod readiness probe 通过

新 Pod 跑起来,K8s 发 GET /health (默认 10s 一次)
期待: 200 OK ─▶ Pod 进入 Ready 状态

⚠️ 这就是为什么 0001 我们说"必须修 /health 不能被 ApiKeyGuard 误伤"。

第 3 步: 旧 Pod readiness probe 失败 / 或 endpoint 摘除

Service Controller 收到 endpoint 更新 ─▶ Service 不再把流量打到旧 Pod
(K8s 默认等 5-10s 让旧 Pod 上的"现存请求"自然结束)

第 4 步: preStop hook (可选,Pod spec 配的)

比如 sleep 5 给 K8s 自己一点时间把 endpoint 摘掉,避免新请求涌入

第 5 步: SIGTERM 发到旧 Pod 的 1 号进程

容器 runtime 拿到指令 ─▶ 给 PID 1 发 SIGTERM

第 6 步: 等待 terminationGracePeriodSeconds(默认 30s)

你的进程可以在这 30 秒里:
  ✓ 停止接受新 HTTP 请求
  ✓ 等 in-flight 请求跑完
  ✓ 关 RabbitMQ / Redis / MySQL 连接(发 ack, 不丢消息)
  ✓ 刷日志 / 关闭文件句柄
  ✓ process.exit(0)

🟢 这就是"软死"。30 秒够大多数应用做完整 cleanup。

第 7 步: 30 秒到点,进程还没退

SIGKILL(9) ─▶ 内核强制,无 cleanup ─▶ 你的 in-flight 请求被打断,连接被切断

🔴 这就是"硬死"。每次发生都要查"为什么没在 30s 内退"。

第 8 步: 新 Pod 接管流量

Service endpoint 更新 ─▶ 流量打到新 Pod

把这 8 步放心里 — backend 工程师做 oncall,被叫醒处理"Pod 启动慢"或者"Pod 关不掉",几乎都跟其中某一步有关。

4. app.enableShutdownHooks() 内部

NestJS 的 enableShutdownHooks() 是把 §3 第 6 步"程序化"的关键: 不开它,SIGTERM 默认直接走 Node 默认行为(立即退出);开了它,NestJS 监听 SIGTERM/SIGINT/SIGUSR2,触发一串有序的 lifecycle 钩子:

收到 SIGTERM
    │
    ▼
OnModuleDestroy    (按依赖逆序调用每个 module 的实现)
    │               ─ 关闭 RabbitMQ 连接,发 nack
    │               ─ 关闭 Redis 客户端
    │               ─ 等待 in-flight 业务操作完
    ▼
beforeApplicationShutdown  (应用级别,所有 module 都已 destroy 完)
    │                       ─ 关掉外部定时任务调度
    ▼
HTTP server 停止接受新请求 (NestJS 内部)
    │
    ▼
OnApplicationShutdown
    │               ─ 刷日志到磁盘
    │               ─ 关闭文件句柄
    ▼
process.exit(0)  (默认,如果 30s 内你退出了)

三件需要记住的:

  1. 这些钩子默认关闭 — 因为监听信号有一点点性能成本,NestJS 让你显式开启
  2. 钩子触发顺序是依赖逆序 — 子 module 先于父 module,跟 §3 第 6 步"先关内层再关外层"对应
  3. 钩子超时由 K8s 的 terminationGracePeriodSeconds 控制 — 你的代码里 30s 内跑不完,K8s 直接 SIGKILL,跟没写钩子一样

5. 动手 · 25 分钟

3 个文件改动,目的:看 kill -SIGTERM 触发 4 阶段有序退出。

5.1 · 在 main.ts 加 app.enableShutdownHooks()

打开 apps/gateway/src/main.ts,在 app.enableCors(...) 后面加一行:

app.enableCors({ ... });
app.enableShutdownHooks();

注意 0001 加的 console.log 探针和 0002 加的 process.on 钩子保留,我们会在收尾时一起删掉 console.log(因为它会在每次启动都打,生产里会刷屏)。

5.2 · 新建 LifecycleProbeService

新建文件 apps/gateway/src/lifecycle/lifecycle-probe.service.ts:

import { Injectable, OnModuleDestroy, OnApplicationShutdown } from '@nestjs/common';

@Injectable()
export class LifecycleProbeService implements OnModuleDestroy, OnApplicationShutdown {
  onModuleDestroy() {
    console.log('[Lifecycle] OnModuleDestroy: closing connections (simulated)');
  }
  onApplicationShutdown(signal?: string) {
    console.log(`[Lifecycle] OnApplicationShutdown: signal=${signal}, flushing logs (simulated)`);
  }
}

这个 service 是"教学用探针",它不做真实清理(没接 RabbitMQ/Redis,不能真关),只打日志,让你看到阶段顺序。生产里应该让它真的关掉对应的连接。

5.3 · 注册到 AppModule

打开 apps/gateway/src/app.module.ts,把 LifecycleProbeService 加到 providers 数组里(跟在 ProxyService 后面):

providers: [
  ProxyService,
  LifecycleProbeService,   // ← 新加
  { provide: APP_GUARD, useClass: CasGuard },
  ...
],

5.4 · 验证 SIGTERM 触发 4 阶段

  1. 重启 gateway:pnpm start:gateway — 留意启动日志第一行 PID,比如 Nest] 14420 就是 PID
  2. 新开一个终端:kill -SIGTERM 14420(用你看到的实际 PID 替换)
  3. 回到 gateway 终端,期望看到(按顺序):
    [Lifecycle] OnModuleDestroy: closing connections (simulated)
[Lifecycle] OnApplicationShutdown: signal=SIGTERM, flushing logs (simulated)
Gateway ... (无新日志)
[进程退出码 0]
  4. 对比实验:把 5.1 那一行 app.enableShutdownHooks() 注释掉,重启,再 kill -SIGTERM — gateway 会立即死,没有 [Lifecycle] 日志。这证明钩子是被 enableShutdownHooks 激活的

这个对比实验非常关键 — 它会让你直观看到"软死 vs 硬死"的差别。生产上"软死"就是靠这 30 秒的窗口期做清理。

commit message(直接复制):

feat(gateway): enable graceful shutdown via NestJS lifecycle hooks

- Add app.enableShutdownHooks() so SIGTERM/SIGINT trigger
  OnModuleDestroy, beforeApplicationShutdown, OnApplicationShutdown
  in dependency-reverse order
- Add LifecycleProbeService that logs at each phase, giving us a
  visible hook for future real cleanup (RabbitMQ/Redis/MySQL close)
- Without this, gateway hard-exits on SIGTERM, dropping in-flight
  requests, unsent RabbitMQ acks, and leaked Redis connections
- K8s default terminationGracePeriodSeconds (30s) is plenty for
  our cleanup work
