1. 单元测试 vs e2e — 两条腿走路

0013 给 3 个 service 装了"逻辑单测"。但单元测试有一个盲区:

RolesGuard 单测通过 ≠ 整个 auth 流程对。RolesGuard 只测了"角色匹配"那 20 行代码,
HTTP 路由 / DTO 验证 / 密码哈希 / JWT 签名 / Cookie 设置 / DB 写入 / Redis 缓存
这一整条链路任一环断了,单测不会报。

单元测试 (0013)

测什么:一个函数 / 一个 service 的纯逻辑

速度:~10ms / 测试

依赖:mock 一切外部 IO

盲区:不验证 HTTP / DB / 真实集成

e2e 测试 (本节)

测什么:一条完整的用户故事(HTTP in/out)

速度:~100ms / 测试

依赖:真 HTTP,选择性真 DB / mock IO

价值:覆盖单元测试的所有集成盲区

两条腿都站住 = principles 轨道写的代码有了"双层安全网"。

2. Supertest + NestJS Testing module

2.1 Supertest — 启动一个 in-memory HTTP server

import * as request from 'supertest';
import { Test } from '@nestjs/testing';
import { AppModule } from '../src/app.module';

const moduleRef = await Test.createTestingModule({
  imports: [AppModule],
}).compile();

const app = moduleRef.createNestApplication();
await app.init();

// ← supertest 把 NestJS app 包成"可发 HTTP 请求"的 server
return request(app.getHttpServer())
  .post('/api/auth/register')
  .send({ username: 'alice', password: 'pwd123456' })
  .expect(201);

关键点:app.getHttpServer() 拿到 Express 实例,supertest 直接打,不开端口、不占 socket。

2.2 Test.createTestingModule — 比 NestFactory.create 多 3 个能力

能力用法
.overrideProvider(X)用 mock 替换某个 provider(本节重点)
.overrideGuard(X)跳过某个 guard(常用于测试带鉴权的接口)
.overrideModule(X)替换整个 module 的 imports

本节我们只用 overrideProvider。

3. 外部依赖隔离策略 — 真 MySQL + mock Redis

e2e 测试要回答的核心问题:哪些外部依赖用真的?哪些 mock?

auth-service 有 3 类外部依赖:

依赖作用0014 选择理由
MySQL存 users 表真SQL bug 是 e2e 最该抓的;docker-compose 已起
Redis存 refresh tokenmock业务简单(set/get/del);mock 教学价值高
bcrypt / JWT密码哈希 + token 签名真纯 CPU,不接 IO,跟"真"没差

经验法则:

  • 用真的:DB(Drizzle/SQL/事务)、加密、JWT、HTTP 客户端(对内)、第三方 SDK
  • 用 mock:缓存(Redis)、消息队列(RabbitMQ)、外部 HTTP API(支付/邮件)、时间/随机数

4. 动手 · 给 auth-service 写 e2e 测试

目标链路:register → login → /me → refresh → logout — 5 个 endpoint,5 个 it()。

4.1 · Mock RedisService

Redis 在 auth-service 里只做 3 件事:get / set / del。我们写一个 in-memory Map 替身。

新建 apps/auth-service/src/redis/redis-memory.service.ts:

import { Injectable, OnModuleDestroy } from '@nestjs/common';

/**
 * e2e 用的 in-memory Redis 替身
 * 接口跟 RedisService 完全一致(get/set/del),但数据存在 Map 里
 */
@Injectable()
export class RedisMemoryService implements OnModuleDestroy {
  private store = new Map<string, { value: string; expiresAt?: number }>();

  async get(key: string): Promise<string | null> {
    const entry = this.store.get(key);
    if (!entry) return null;
    if (entry.expiresAt && Date.now() > entry.expiresAt) {
      this.store.delete(key);
      return null;
    }
    return entry.value;
  }

  async set(key: string, value: string, ttlSeconds?: number): Promise<void> {
    this.store.set(key, {
      value,
      expiresAt: ttlSeconds ? Date.now() + ttlSeconds * 1000 : undefined,
    });
  }

  async del(key: string): Promise<void> {
    this.store.delete(key);
  }

  // 给测试用:清空整个 store
  clear(): void {
    this.store.clear();
  }

  onModuleDestroy() {
    this.store.clear();
  }
}

设计要点:接口完全照搬 RedisService(同样方法签名),这样可以靠 NestJS DI 的同 token 替换:

// 在 e2e 里:
.overrideProvider(RedisService).useClass(RedisMemoryService)

4.2 · 写 e2e 测试

新建 apps/auth-service/test/auth.e2e-spec.ts:

import { Test, TestingModule } from '@nestjs/testing';
import { INestApplication, ValidationPipe } from '@nestjs/common';
import request from 'supertest';  // ← supertest 7.x 是 default export,不是 namespace
import { eq } from 'drizzle-orm';
import { AppModule } from '../src/app.module';
import { RedisService } from '../src/redis/redis.service';
import { RedisMemoryService } from '../src/redis/redis-memory.service';
import { DrizzleService } from '../src/database/drizzle.service';
import { users } from '../src/database/schema/users';

describe('Auth Flow (e2e)', () => {
  let app: INestApplication;
  let redis: RedisMemoryService;
  let drizzle: DrizzleService;

  // 每个 e2e 跑用唯一 username — 避免本地/CI 重复跑冲突
  const username = `alice_${Date.now()}_${Math.random().toString(36).slice(2, 8)}`;
  const password = 'pwd123456';
  let accessToken: string;

  beforeAll(async () => {
    const moduleRef: TestingModule = await Test.createTestingModule({
      imports: [AppModule],
    })
      // ← 核心:overrideProvider 替换 RedisService 为 in-memory 版本
      .overrideProvider(RedisService)
      .useClass(RedisMemoryService)
      .compile();

    app = moduleRef.createNestApplication();
    // main.ts 里也开了 ValidationPipe,e2e 同样开起来
    app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));
    await app.init();

    // override 之后,用原 token (RedisService) 拿到的就是替换后的实例
    redis = moduleRef.get(RedisService) as RedisMemoryService;
    drizzle = moduleRef.get(DrizzleService);
  });

  afterAll(async () => {
    // 清理测试用户 — 用 drizzle 的 delete API
    await drizzle.db.delete(users).where(eq(users.username, username));
    await app.close();
  });

  afterEach(() => {
    redis.clear();   // 每个 it 之间清空 in-memory store
  });

  // ───────────────────── happy path ─────────────────────

  it('POST /api/auth/register creates a new user (201)', async () => {
    const res = await request(app.getHttpServer())
      .post('/api/auth/register')
      .send({ username, password, email: `${username}@test.com` })
      .expect(201);

    expect(res.body).toMatchObject({
      username,
      email: `${username}@test.com`,
      role: 'user',
    });
    expect(res.body).not.toHaveProperty('passwordHash');
  });

  it('POST /api/auth/login returns accessToken + sets refresh cookie (201)', async () => {
    const res = await request(app.getHttpServer())
      .post('/api/auth/login')
      .send({ username, password })
      .expect(201);

    expect(res.body.accessToken).toBeDefined();
    expect(res.body.user).toMatchObject({ username, role: 'user' });

    const cookies = res.headers['set-cookie'];
    expect(cookies).toBeDefined();
    // supertest 把 set-cookie 当 string,但 Express 实际返 string[]
    const cookieArr = Array.isArray(cookies) ? cookies : [cookies];
    expect(cookieArr.some((c: string) => /refreshToken=[^;]+/.test(c))).toBe(true);
    expect(cookieArr.some((c: string) => /HttpOnly/i.test(c))).toBe(true);

    accessToken = res.body.accessToken;
  });

  it('GET /api/auth/me returns user when given valid Bearer token (200)', async () => {
    const res = await request(app.getHttpServer())
      .get('/api/auth/me')
      .set('Authorization', `Bearer ${accessToken}`)
      .expect(200);

    expect(res.body.user).toMatchObject({ username, role: 'user' });
    expect(res.body.user).not.toHaveProperty('passwordHash');
  });

  // ───────────────────── failure paths ─────────────────────

  it('GET /api/auth/me returns user=null with invalid token (200)', async () => {
    const res = await request(app.getHttpServer())
      .get('/api/auth/me')
      .set('Authorization', 'Bearer not-a-real-token')
      .expect(200);

    expect(res.body.user).toBeNull();
  });

  it('POST /api/auth/register rejects duplicate username with 409', async () => {
    await request(app.getHttpServer())
      .post('/api/auth/register')
      .send({ username, password })
      .expect(409);
  });

  it('POST /api/auth/login returns 401 on wrong password', async () => {
    await request(app.getHttpServer())
      .post('/api/auth/login')
      .send({ username, password: 'wrong-password' })
      .expect(401);
  });

  it('POST /api/auth/register returns 400 on password too short', async () => {
    await request(app.getHttpServer())
      .post('/api/auth/register')
      .send({ username: 'bob', password: '123' }) // @MinLength(6)
      .expect(400);
  });
});

注意:

  • 文件位置:test/ 目录(不是 src/),跟 tsconfig.spec.json 的 include: ["apps/**/*.ts"] 匹配
  • 文件命名:auth.e2e-spec.ts — 这是 NestJS 官方约定的 e2e 命名
  • jest.config.js 必须把 *.e2e-spec.ts 也加进 testMatch(见 4.0 步骤)
