限流与安全:让 gateway 学会说"不"

没限流的 gateway = 任意客户端可以在 1 秒内发 10000 个请求把你的进程 / 下游服务打爆。

  1. 理解限流的两大参数: TTL(时间窗) + Limit(限额)
  2. 用 @nestjs/throttler 装上全局限流,默认 100 req/min

1. 为什么需要限流

考虑这三种"事故",每一种都真实发生过:

场景后果
前端 bug 写错死循环,每 10ms 调一次登录auth-service CPU 100%,所有用户登不上
恶意用户拿脚本刷 /api/auth/login 猜密码数据库被慢查询塞满,所有业务慢
DDOS 攻击gateway 进程被请求淹没,正常用户全 502

限流是"主动拒绝"机制 — 在请求被处理之前,根据调用方身份或IP判断"你已经在窗口里用了多少次了,超了就不让进"。

2. Throttler 心智模型:3 个关键概念

ThrottlerModule.forRoot([{
  ttl: 60_000,   // 1 分钟时间窗(毫秒)
  limit: 100,    // 这个窗口里最多 100 次
}])

三个核心元素:

概念含义类比
ttl时间窗大小(毫秒)60_000 = 1 分钟"过去 1 分钟内"
limit窗口内允许的最大请求数"不能超过 100 次"
ThrottlerGuard实际的"看门人",每次请求判断"超没超""保安"

超出 → 自动 429 Too Many Requests 响应(无业务代码介入,Guard 直接拒)。

还可以定义多窗口叠加(每个都通过才算"未超"):

ThrottlerModule.forRoot([
  { name: 'short', ttl: 1_000,   limit: 5 },     // 1 秒内最多 5 次
  { name: 'long',  ttl: 60_000,  limit: 100 },   // 1 分钟内最多 100 次
])

攻击者 1 秒发 1000 个请求 → short 窗口 5 个就拒了,根本到不了业务代码。

3. Counter 存在哪?

默认存当前进程的内存 Map(ThrottlerStorageService)。这意味着:

  • 多实例部署时,每个实例独立计数 — 实际限额 = 配置值 × 实例数
  • 实例重启,counter 归零

多实例 production 通常用 Redis 存 counter(下节课 0008 讲)。本节课用默认 in-memory,够 demo。

4. 动手 · 5 个文件改动

4.1 · 装 @nestjs/throttler

pnpm add -w @nestjs/throttler

4.2 · AppModule 注册 ThrottlerModule + ThrottlerGuard

打开 apps/gateway/src/app.module.ts,加 import + 在 providers 数组加 ThrottlerGuard:

import { ThrottlerModule, ThrottlerGuard } from '@nestjs/throttler';

@Module({
  imports: [
    ConfigModule.forRoot({ isGlobal: true }),
    LoggerModule.forRoot({ ... }),
    HealthModule,
    ThrottlerModule.forRoot([     // ← 新加
      { name: 'short', ttl: 1_000, limit: 5 },
      { name: 'long', ttl: 60_000, limit: 100 },
    ]),
  ],
  providers: [
    ...
    {
      provide: APP_GUARD,
      useClass: ThrottlerGuard,   // ← 新加,全局生效
    },
  ],
})

现在每个请求都被计数。两次窗口任一超限 → 429。

4.3 · /health 加 @SkipThrottle()

打开 apps/gateway/src/health/health.controller.ts,每个 handler 加 @SkipThrottle():

import { SkipThrottle } from '@nestjs/throttler';

@Public()
@SkipThrottle()         // ← 新加
@Get('live')
@HealthCheck()
liveness() { ... }

@Public()
@SkipThrottle()         // ← 新加
@Get()
@HealthCheck()
readiness() { ... }

原因: K8s probe 每 5-10 秒就 ping 一次 /health,如果不 skip 会被限流,然后 K8s 觉得"服务挂了"重启 pod,陷入循环。

4.4 · 给敏感端点加更严的 @Throttle

打开 apps/gateway/src/app.controller.ts,给 /api/auth/login 加 @Throttle 覆盖默认:

import { Throttle } from '@nestjs/throttler';

@ApiOperation({ summary: "用户登录(代理到 auth-service)" })
@ApiResponse({ status: 200, description: "登录成功" })
@ApiResponse({ status: 401, description: "凭证错" })
@ApiResponse({ status: 429, description: "请求过于频繁" })
@Throttle({ default: { limit: 5, ttl: 60_000 } })   // ← 新加:1 分钟最多 5 次
@Post("api/auth/login")
async login(@Body() body: any) { ... }

防爆破: 1 分钟最多 5 次,密码错误次数再多也进不了 — 同时慢下来阻止暴力枚举。

4.5 · 验证 4 件事

  1. 重启 pnpm start:gateway
  2. 验证 /health 不被限流(连发 20 次应该都 200): 
    for i in {1..20}; do curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/health; done | sort | uniq -c
    期望: 20 200(没 429,说明 @SkipThrottle 生效)
  3. 验证 /api/auth/me(普通端点)按 long 窗口限流(快速 110 次): 
    for i in {1..110}; do curl -s -o /dev/null -w "%{http_code}\n" -H "X-API-Key: ds_key_123" http://localhost:3000/api/auth/me; done | sort | uniq -c
    期望: 大约 100 401 + 10 429(前 100 个穿透,后 10 个被限)
  4. 验证 /api/auth/login 按更严的 5/min 限流(快速 10 次): 
    for i in {1..10}; do curl -s -o /dev/null -w "%{http_code}\n" -X POST -H "Content-Type: application/json" -d '{"username":"a","password":"b"}' http://localhost:3000/api/auth/login; done | sort | uniq -c
    期望: 5 401 + 5 429(5 次过后被更严的限流拒)
  5. 看控制台 — 应该有 0005 装的 Pino 格式 429 日志

4.5 步骤 3 是这一节"金样本" — 看到第 6 次登录就 429,你会突然理解"为什么 app 总在'我密码对了为啥不让登'"。

commit message(直接复制):

feat(gateway): rate limiting with @nestjs/throttler

- Register ThrottlerModule globally with two stacked windows:
  5 req/sec + 100 req/min. ThrottlerGuard registered as APP_GUARD
  applies to all routes by default
- Skip throttling on /health/live and /health/readiness so K8s
  probes aren't rate-limited (would cause restart loops)
- Override /api/auth/login to stricter 5 req/min limit to
  prevent credential brute force
- Multi-window design: attack spike gets caught by short window
  before reaching downstream services

Refs: docs/teaching/lessons/0007-rate-limiting.html
